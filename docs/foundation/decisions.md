# 設計決策

這裡記錄「看起來可以換成更常見的做法、但刻意不換」的決定：是什麼、為什麼、代價，以及什麼時候該重新檢討。
想改掉其中一項之前先讀那一條，確認情境是不是真的變了。只寫現況；決定改了就直接改寫那一條
（這是 foundation 這一份的寫法，[不是子專案的規則](workflow.md#foundation-只寫現況)）。

**編號不重用、不重排**：刪掉一條時編號留空，新增的一律接在最後。子專案與程式碼的註解用編號指回這裡。

這一份歸 foundation，子專案不改。專案自己的決定、推翻了這裡的哪幾條，寫在
[`docs/project/`](../project/README.md)。

## 1. 用 `auth_version` 撤銷登入，不做 refresh token

每個使用者有 `auth_version`，簽進登入憑證，每個請求跟資料庫比對。撤銷就是 +1（改密碼、登出、停用、
`make db revoke-sessions`）。憑證到期就要重新登入，不續期。

- **為什麼**：每個請求本來就要查使用者，順便比對不多一次查詢；不必多一套 refresh token 的儲存與續期流程。
- **代價**：到期一定登出，即使正在操作；登出會讓那個帳號的所有裝置一起登出。
- **重新檢討**：需要「保持登入」、只登出單一裝置，或對外開放給大量使用者時。

## 2. 網頁不開註冊，超級管理者只能用指令建立

- **為什麼**：網頁上任何建立高權限帳號的入口，都是一組要保管的秘密或一個可以搶註的空窗。
  只能用指令時，前提就是握有主機的 shell。
- **代價**：沒有 email，忘記密碼只能請管理者重設；要自助註冊得自己開發。
- **重新檢討**：要開放外部使用者自助註冊時。

## 3. 權限與語系集中定義，不由模組動態註冊

`Permission` 與 `Language` 是集中的 enum，是僅有的兩處「新增功能要改共用檔案」的地方。

- **為什麼**：動態註冊的值在 OpenAPI 裡只是 `string`；集中成 enum，前端打錯權限名稱是編譯錯誤，不是執行期靜默失效。
- **代價**：新增或移除模組時要記得改 enum（漏了宣告啟動會失敗）。
- **重新檢討**：模組要做成可以獨立安裝的套件時。

## 4. 背景任務放 PostgreSQL，佇列自己寫

- **為什麼**：任務與業務資料在同一個交易裡，不會出現「資料沒寫進去、任務卻執行了」；少一個要維運與備份的服務。
  現成的 PostgreSQL 佇列套件接不上專案的 SQLAlchemy 連線與 migration，拿不到同一個交易。
- **代價**：取任務、重試、回收、排程的邊界情況要自己用測試守住；吞吐量不如專門的佇列。
- **重新檢討**：需要管理畫面、流程編排、每秒上百個任務，或自寫的部分反覆出同類錯誤時。

## 5. 限流計數放 PostgreSQL，不引入 Redis

- **為什麼**：計數共用之後 api 才能開多個行程；只有登入與改密碼需要限流，為此多一個服務不划算。
- **代價**：每次檢查多一次資料庫寫入；用固定時間窗，窗口交界時最多放行兩倍的次數。
- **重新檢討**：限流要用在高流量的端點時。

## 6. 部署時短暫停機

部署時先停掉對外入口與舊版服務，跑完 migration、新版通過健康檢查之後才接回流量；失敗就停在維護狀態。

- **為什麼**：零停機要新舊版本同時在線，migration 也要寫成兩版相容；對內部系統不值得這個複雜度。
  先停再改資料表，才不會有舊程式配新結構的空窗。
- **代價**：每次部署中斷幾十秒（手上有長任務時更久），要挑離峰時段；部署失敗時服務是停著的，要有人處理。
- **重新檢討**：不能接受部署時中斷時。先確認 migration 的寫法能讓兩版共存。

## 7. 初始資料由 migrate 服務寫入

- **為什麼**：api 開機時寫入，多個行程會競爭，失敗時服務已經切換；寫成資料 migration，發版後就不能改。
  放在 migrate 服務，失敗跟 migration 失敗一樣擋下部署。
- **代價**：系統角色在資料庫裡的改動會在下次部署被蓋回來（刻意的）。
- **重新檢討**：要讓使用者在後台改系統角色、而且改動要保留時。

## 8. 錯誤追蹤預設關閉

log、request id、AUDIT 與 `make doctor` 是內建的；錯誤追蹤（Sentry、GlitchTip）要設 `SENTRY_DSN` 才啟用。

- **為什麼**：錯誤內容可能帶著使用者的資料，送不送第三方是專案的決定。
- **代價**：沒設定時出錯沒有人收到通知，要有人去看 `make logs errors`。
- **重新檢討**：上線給外部使用者，或需要主動發現錯誤時，設定它。

## 9. 部署主機上放整份 repo

- **為什麼**：維運指令（備份、還原、檢查）在 `tools/` 與 `infra/`，跟著版本走；主機與開發機用同一套指令。
- **代價**：主機上有整份原始碼；上線的版本一定要先發 tag。
- **重新檢討**：改用容器平台、主機不再執行維運指令時。

## 10. 部署不設 environment reviewer

發布前的確認在 agent 這一側（`release` skill 與 hook），GitHub 的 environment 不設 Required reviewers。

- **為什麼**：只有一位維護者、與 agent 用同一個 GitHub 帳號；一組有多套系統時每套都要按一次核准。
- **代價**：防線只在 agent 這一側，hook 沒載入或換了寫法就擋不住。
- **重新檢討**：agent 在沒人看著的環境執行、有第二位維護者，或 agent 改用自己的帳號時，改設 Required reviewers。

## 11. agent 的防線以判斷為主，hook 只擋確認點

- **為什麼**：用 hook 逐一解析 shell 寫法去擋，每補一種就出現下一種，誤擋也越來越多。
  兩家的 agent 都讀得懂規則，不確定時會問。
- **代價**：判斷錯誤要到 CI 或審查才發現；用 shell 改測試檔不會被攔。
- **重新檢討**：agent 在沒人可以問的環境執行時，改用更嚴格的 hook 或 GitHub 端的關卡。

## 12. 跨模組只以 ID 參照，但保留外鍵與共用交易

程式層不 import 別的模組的資料表；資料庫層照樣建外鍵，跨模組的呼叫也在同一個交易裡。

- **為什麼**：程式層嚴格，模組才能整包移除、內部才改得動；資料庫層寬鬆，因為沒有拆成多個服務的計畫，
  資料一致性用很低的成本就拿得到。
- **代價**：比 JOIN 多幾次查詢（固定次數，不隨筆數增加）；要用別的模組的欄位排序時得另外處理。
- **重新檢討**：真的要把某個模組拆成獨立服務時。

## 13. 回應在交易 commit 之後才送出

回應先收在記憶體，交易 commit 成功才送給用戶端。

- **為什麼**：用戶端收到成功時資料一定已經寫入，緊接著的下一個請求讀得到；commit 失敗也來得及改回錯誤。
- **代價**：不支援串流回應（大檔下載、Server-Sent Events）。
- **重新檢討**：需要串流時，讓那幾條路由繞過這個處理，並自己管交易。

## 14. 手機上鎖住畫面縮放

viewport 設 `maximum-scale=1`、根元素 `touch-action: manipulation`、觸控裝置的輸入框字級至少 16px。

- **為什麼**：前端要在手機上像原生 App；可以縮放時固定的標題列與底部導覽會跟著跑掉。
- **代價**：不能用雙指放大畫面，無障礙檢測會扣分。
- **重新檢討**：使用者包含需要放大畫面的族群，或要符合無障礙規範時，拿掉 viewport 的那兩項。

## 15. TypeScript 停在 5.9

- **為什麼**：`openapi-typescript` 只支援 5，`typescript-eslint` 只支援到 6.0；產生契約型別的工具穩定比新重要。
- **代價**：用不到新版的功能與速度。TypeScript 只在開發與建置時使用，不進正式環境。
- **重新檢討**：`npm view openapi-typescript peerDependencies` 與 `npm view typescript-eslint peerDependencies`
  都放寬時升級。

## 16. AUDIT 寫入資料表失敗時不補寫

每筆 AUDIT 先寫進 log，請求結束後才另開交易寫進 `audit_logs`；後面這一步失敗時只記一行
`audit_flush_failed`，不重試也不擋下請求。

- **為什麼**：要保證不遺漏，得把紀錄與業務資料放進同一個交易（失敗的操作就留不下紀錄），或另外維護
  一個可靠的補寫佇列；目前沒有正式的稽核要求，不值得這個複雜度。log 那一份一定先寫，查得回來。
- **代價**：資料庫在那個瞬間寫不進去時，資料表會少那幾筆，要從 log 找
  （`make logs errors` 看得到 `audit_flush_failed`，用同一個 request id 找回事件內容）。
- **重新檢討**：有法規或合約要求稽核紀錄完整保存時。做法是失敗的那批改排成背景任務重試，並對
  `audit_flush_failed` 設告警。

## 17. 子專案用 skill 同步 foundation，不用 git 的 upstream

子專案在 `.foundation.json` 記下上次同步到的 foundation commit，`sync-foundation` skill 取出那之後的改動，
逐檔做三方比對（[做法](workflow.md#與-foundation-同步)）。

- **為什麼**：`main` 一律 squash merge，`git merge upstream/main` 的 merge commit 會被壓掉，下次同步時 Git
  不知道哪些已經合過，解過的衝突全部重來。把同步點記在檔案裡就不受合併方式影響；foundation 的 tag 也不會
  被抓進子專案而誤觸部署。
- **代價**：兩個 repo 沒有共同歷史，`git log` 看不到某一行來自 foundation 的哪個 commit；同步靠腳本與 agent，
  不是 Git 內建的指令。
- **重新檢討**：子專案改成保留 merge commit，或 foundation 的內容改用套件發布時。
